# REGISTRATION — the provenance stamp and the retention policy

Registration owed #9. Written because R-1 in `RETRACTIONS.md` had to withdraw two claims for want of
a field that costs four lines to write, and the same omission will withdraw the next two unless the
rule exists before the next run.

## 1. The stamp — what every summary must carry, from the next run onward

A `provenance` object at the top level of every result JSON. Every field is obtainable without a
network call and without any dependency the runs do not already have.

| field | source |
|---|---|
| `gpu_name` | `torch.cuda.get_device_name(0)` |
| `gpu_count` | `torch.cuda.device_count()` |
| `cuda_runtime` | `torch.version.cuda` |
| `driver` | `torch.cuda.driver_version()` if available, else the `nvidia-smi --query-gpu=driver_version` line the launcher already runs |
| `torch` | `torch.__version__` |
| `transformers` | `transformers.__version__` |
| `transformer_lens` | `transformer_lens.__version__` |
| `python` | `sys.version.split()[0]` |
| `dtype` | the dtype actually passed to `from_pretrained_no_processing` |
| `lambda_instance_id` | the launcher's instance id, passed in via env — **the field that makes the audit log joinable** |
| `git_commit` | `git rev-parse HEAD` at launch, so the instrument version is pinned |
| `started_utc`, `finished_utc` | ISO-8601 |

**`lambda_instance_id` and `started_utc` are the load-bearing pair.** Lambda's
`GET /api/v1/audit-events` records `instance_type` per launch, so with either of those two fields an
artifact's hardware becomes recoverable from the audit log after the fact. Without them the audit log
and the artifacts are two lists that cannot be joined — which is exactly why [69] and [70] are
withdrawn rather than repaired.

For offline / CPU-only instruments the GPU fields are `null` and the library and `git_commit` fields
are still required: `out/gapclose_foldrate_sig.json`'s p-values depend on whether `scipy` was
importable, and an artifact that does not say which path it took is not reproducible either.

**Enforcement, so this does not decay into a convention nobody applies:** a selftest assertion in each
new instrument that `provenance` is present with every key, and — the cheap catch-all — a standing
check that fails if any newly written summary lacks the object. Retrofitting the 323 existing
artifacts is not proposed: their runs are gone, and a stamp written now would be a fabrication.

## 2. The retention policy — and what the current one actually did

The present policy is two `.gitignore` globs, and nobody chose its outcome:

```
21: *captures*.npz
22: think_probe_capture*.npz
```

Measured now, across every `.npz` named by a result JSON:

| capture | status | named by |
|---|---|---|
| `phase3_handles_p3a_{2bit,9bit,27b}.npz` | **PRESENT, all three** | 5 result JSONs |
| `phase3c_captures_p3c_{2bit,9bit,27b}.npz` | ABSENT | 6 result JSONs |
| `think_probe_capture_tp_9bit_comb.npz` | ABSENT | 1 result JSON |

The handles files survived **because their names match neither glob**, not because anyone decided the
handles were worth keeping and the captures were not. Four distinct captures are gone and **eight**
result JSONs reference them — the reconciled ledger says five, which undercounts.

The consequence is asymmetric in a way worth stating plainly: the phase-3a write-side handles at all
three scales are reproducible, and every phase-3c / phase-4 / think-probe number is not. That is the
difference between the write-side derivation and the belief-state read being independently checkable.

**Policy, registered:**

1. A capture that any committed result JSON *names* is retained. If it is too large for the git pack,
   it goes to a bucket and the artifact records the URI and a SHA-256 — the artifact must not name a
   path that resolves to nothing.
2. A capture nothing names is regenerable scratch and stays ignored.
3. The globs are replaced by an explicit list, so retention is a decision rather than a
   pattern-match accident.
4. Every capture reference is stored **POSIX-relative to the repo root**. Four current references are
   Windows-style (`results_foldlisten_p3c\out\phase3c_captures_p3c_9bit.npz`), which will not resolve
   on this workstation even if the file is restored.

## 3. What this does not claim

Nothing here recovers a past run. The three absent capture families can only be regenerated by a GPU
pass, and until they are, the phase-3c / phase-4 / think-probe numbers remain what the reconciled
ledger classed them: the repo's single largest instrument debt, blocking zero written claims. This
registration makes the *next* run's numbers auditable; it does not make the last one's so.
